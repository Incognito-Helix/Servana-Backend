## 1. Overview

Servana helps customers find local vendors (caterers, barbers, makeup artists, designers and so on) near them. Vendors get one profile. Customers search by service and area, then call or WhatsApp the vendor. Listing is free. Servana makes money by selling boosts that push vendors to the top of search in the zones they pay for.

The backend owns all business rules. The frontend never sorts results, never computes prices and never marks a boost live. It shows what the API returns.

Work through the steps in order. Each step lists what to build, the rules to enforce and the checks that prove it works.

## 2. Core rules (read before coding)

These come from the PRD. Every step below has to respect them.

### Users and roles
- Three roles: customer, vendor, admin. Visitors can browse without an account.
- Admin accounts are never created through public sign up. Only the seed script or another admin creates them.
- Suspended accounts cannot log in, by password or by Google.

### Vendors
- A vendor profile goes live only after the NIN check passes and an admin approves it.
- Profile statuses: draft, pending, approved, rejected, suspended. Only approved profiles show in search, the home feed and `/p/:slug`.
- Free tier vendors can change their base location once every 7 days. An active boost lifts that limit.

### Privacy
- Phone and WhatsApp numbers never appear in public profile or search responses. They only come from the contact endpoint.
- The full NIN is never stored or logged. Only the last 4 digits and the result.
- Passwords and password hashes are never returned in any response. OTPs and reset tokens are stored hashed.

### Money
- All money is stored in kobo as integers. Never floats.
- A boost activates only from a verified Paystack webhook, never from the frontend.
- Payment and boost updates run inside database transactions. Webhooks are idempotent.

## 3. Local setup

### 3.1 Prerequisites
- Node.js (LTS)
- Docker Desktop
- Git

### 3.2 First time setup

```bash
git clone https://github.com/Incognito-Helix/Servana-Backend.git
cd Servana-Backend
git checkout staging
npm install
cp .env.example .env        # then fill in the values
docker compose up -d        # starts Postgres on port 5432
npx prisma migrate dev      # creates tables and generates the Prisma client
npx prisma db seed          # loads zones, categories and the admin account
npm run dev                 # API on port 8080
```

Check `http://localhost:8080/health`. It should return 200.

### 3.3 Ports

| What | Port |
|---|---|
| Express API | 8080 |
| PostgreSQL | 5432 |

Never put the API and the database on the same port.

### 3.4 Every time you pull

If someone added a migration, run `npx prisma migrate dev` after pulling. If `package.json` changed, run `npm install`.

## 4. Git workflow

- `staging` is the base branch. Always branch from it:
  ```bash
  git fetch origin
  git checkout -b feat/<short-name> origin/staging
  ```
- Push your own branch the first time with `git push -u origin feat/<short-name>`.
- Open a pull request into `staging`. Merging to `staging` deploys to staging. Production is promoted after a smoke test.
- One card, one branch, where possible.
- Commit messages: `feat:`, `fix:`, `chore:`, `refactor:`, `docs:`, `test:`.
- Never commit `.env` or `node_modules`. Always commit `package-lock.json`.

## 5. Project structure

```
Servana-Backend/
  prisma/
    schema.prisma          all models and enums
    migrations/            generated by prisma migrate, committed
    seed.js                Lagos zones, categories, admin account
  src/
    config/                shared Prisma client, env checks, constants
    controllers/           request and response handling only
    services/              business logic (ranking, boosts, pricing)
    middlewares/           auth, roles, validation, rate limits, errors
    models/                validation schemas
    routers/               route definitions
    app.js                 Express app and middleware
  server.js                loads env, starts the server
  docker-compose.yml       local Postgres
  .env.example             committed template
```

Rule of thumb: controllers stay thin. Anything with a business rule goes in a service.

## 7. Build steps

### Step 1: Foundation

**Build**
- Docker Compose with Postgres 16
- Prisma 6 connection and one shared Prisma client in `src/config/`
- `/health` runs `SELECT 1` through Prisma and returns 200, or 503 if the database is down
- Global error handler and the standard error shape (section 9)
- Full schema from PRD section 7, first migration, seed script

**Schema notes**
- Use camelCase fields in Prisma and `@@map` to snake_case table names
- Enums for every status field listed in the PRD
- Unique: `users.email`, `users.googleId`, `vendor_profiles.slug`, `vendor_profiles.phone`, `payments.paystackReference`
- Composite unique: reviews on (profile, customer), contact_reveals on (profile, customer), boost_zones on (boost, zone)
- Indexes: vendor_profiles (latitude, longitude) and (zoneId), profile_events (profileId, createdAt) and (boostId)
- Categories and zones are deactivated, never deleted

**Seed**
- Lagos zones with centre points and price multipliers (Lekki, Victoria Island and Ikoyi at 1.5, the rest at 1.0)
- Five top level categories with their services: Beauty, Events, Food, Home, Tech and creative
- One admin account

**Done when**
- [ ] `docker compose up -d` then `npm run dev` starts cleanly
- [ ] `/health` returns 200, and 503 when the database is stopped
- [ ] `npx prisma migrate dev` runs on a clean database without errors
- [ ] `npx prisma db seed` loads zones, categories and the admin

### Step 2: Authentication

**Endpoints**
`/auth/register`, `/auth/verify-email`, `/auth/login`, `/auth/google`, `/auth/logout`, `/auth/me`, `/auth/forgot-password`, `/auth/reset-password`, `/auth/change-password`

**Rules**
- JWT in an httpOnly, Secure, SameSite=Lax cookie. Never in the response body for storage in localStorage
- State changing requests carry a CSRF header
- bcrypt with at least 10 salt rounds
- Email OTP: 6 digits, expires in 10 minutes, stored hashed
- Reset token: single use, expires in 30 minutes, stored hashed
- Rate limit login, OTP and forgot password with express-rate-limit
- Google users count as email verified. A Google email that matches an existing account signs into that account

**Validation**

| Field | Rules |
|---|---|
| `firstName`, `lastName` | 2 to 50 characters, required |
| `email` | Valid format, unique, stored lowercase |
| `password` | At least 8 characters, one uppercase, one number, one special character |
| `confirmPassword` | Must match `password` |
| `role` | `customer` or `vendor` only. `admin` returns 400 |
| `acceptTerms` | Required, must be true |

**Done when**
- [ ] Valid sign up creates an unverified account and sends an OTP
- [ ] Wrong or expired OTP returns 400
- [ ] Invalid login returns 401 with a generic "invalid credentials" message
- [ ] 6th failed login in 15 minutes returns 429
- [ ] Suspended account returns 403 and no cookie is set
- [ ] Forgot password returns the same message whether the email exists or not
- [ ] `/auth/me` returns user, role and email verified status (plus profile status for vendors)
- [ ] Missing or expired cookie on a protected route returns 401

### Step 3: Vendor profile and onboarding

**Endpoints**
`/vendors/profile`, `/vendors/:id`, `/vendors/:id/services`, Cloudinary signed upload endpoint

**Rules**
- Six step wizard, each step saves on its own and stores `onboardingStep`
- Steps: business info, contact and socials, location, services and pricing, photos and hours, NIN
- Submit sets status to pending. Edits to an approved profile go live without going back to pending
- Slug is generated from the business name, unique, and never changes
- Location changes follow the 7 day cooldown unless a boost is active or admin overrides it
- "Works remotely" only when the primary service is under Tech and creative
- Images upload straight to Cloudinary with a signed upload from the API

**Validation**

| Field | Rules |
|---|---|
| `businessName` | 2 to 80 characters, required |
| Primary service | Required, active category. Up to 3 others, no repeats |
| `about` | Up to 500 characters, no phone numbers or emails |
| `phone` | Valid Nigerian number, unique across vendors |
| Location | State, city and zone required. Coordinates inside the Lagos bounding box |
| Services | At least one. Prices in kobo, positive. Max price not below starting price |
| Photos | Cover and profile photo required, at least one portfolio image. JPEG, PNG or WebP, 5 MB max, 10 portfolio max |
| Hours | Open time before close time on each open day |

**Done when**
- [ ] Progress survives a refresh and the vendor resumes on the right step
- [ ] Submit with missing fields returns 400 listing what is missing
- [ ] Unapproved or suspended profile at `/p/:slug` returns 404 to everyone except the owner
- [ ] No public response ever contains phone or WhatsApp
- [ ] Pending vendor requesting a boost quote gets 403

### Step 4: NIN verification

**Endpoint**: `/verifications/nin`

**Rules**
- Mock service behind one function so a real provider can replace it later
- Any 11 digit NIN passes and returns the account name. Ending in `0000` fails as "NIN not found". Ending in `1111` fails as "name does not match"
- Name on the result must match the account first and last name, case insensitive
- Store only the last 4 digits and the result. Exclude this endpoint's request body from all logging
- 3 attempts per vendor per 24 hours
- A passed check locks the NIN and the account name

**Done when**
- [ ] Anything other than exactly 11 digits fails validation before the check runs
- [ ] 4th attempt in 24 hours returns 429
- [ ] Submitting the profile before a passed check returns 400
- [ ] No full NIN anywhere in the database or logs

---

### Step 5: Search and discovery

**Endpoints**: `/search`, `/locations/suggest`

**Rules**
- A location is required before any search
- Narrow with a bounding box on latitude and longitude, then haversine distance in the database
- Default radius 10 km, max 50 km
- Filters: price range (sent in naira, converted to kobo), minimum rating, home service, open now (Africa/Lagos time), location
- 20 results per page, max 50
- Record an impression every time a vendor card is returned

**Ranking (PRD 5.4)**
1. Approved vendors in range or in the zone, plus vendors who boosted that zone for the category, plus remote vendors
2. Top Spot first, then Zone Boost, then organic
3. Within each group, local vendors by distance then rating. Remote vendors after local ones, by rating
4. Max 3 sponsored slots on search, 8 in Popular. Both are config constants
5. Rotate paid vendors fairly, but keep order stable within one session
6. Return results already ranked with a `sponsored` flag

**Done when**
- [ ] No location returns 400
- [ ] Top Spot above Zone Boost above organic, sponsored capped at 3
- [ ] A boost only shows for its own category and boosted zones
- [ ] Suspended or unapproved vendors never appear
- [ ] Search responds in under 1 second with 100 vendors

### Step 6: Contact reveal

**Endpoint**: `/vendors/:id/contact`

**Rules**
- Logged in users with a verified email only
- Up to 20 different vendors per user per day. Repeat reveals of the same vendor do not count
- Log every reveal and every call or WhatsApp tap as a `contact_tap` event, linked to the active boost if there is one
- First reveal creates a `contact_reveals` row. Two days later, send the "Did you hire this vendor?" email

**Done when**
- [ ] No session returns 401, unverified email returns 403
- [ ] 21st different vendor in a day returns 429
- [ ] Unapproved vendor returns 404

---

### Step 7: Reviews

**Endpoints**: `/vendors/:id/reviews`, `/reviews/:id/reply`, `/reviews/:id/report`

**Rules**
- One review per customer per vendor. Rating 1 to 5, comment up to 1,000 characters
- Verified email required. Revealing the number is not required
- Vendor can post one reply per review, up to 500 characters
- Customers and vendors can report reviews. Hidden reviews are left out of the average and count
- Recalculate `avgRating` and `reviewCount` after every new or hidden review

**Done when**
- [ ] Second review for the same vendor returns 409
- [ ] Vendor trying to review returns 403
- [ ] Second reply returns 409
- [ ] Yes on the follow up email adds the Confirmed hire tag

---

### Step 8: Boosts

**Endpoint**: `/boosts`

**Prices (in naira, store in kobo)**

| Boost | Daily | Weekly | Monthly |
|---|---|---|---|
| Zone Boost | 500 | 3,000 | 10,000 |
| Top Spot | 1,000 | 6,000 | 20,000 |

Quote = base price × zone multiplier, added up across chosen zones. The server always computes the price.

**Lifecycle**
- Statuses: pending, active, expired, cancelled
- In effect when active and the current time is between `startAt` and `endAt`
- Existing boost on a chosen zone with under 24 hours left: the new one starts when it ends. More than 24 hours left: 409
- Overlap check runs inside a transaction
- node-cron job: expire boosts past `endAt`, cancel pending boosts older than 30 minutes, send one reminder under 24 hours (`reminderSentAt`). Safe to run twice

**Done when**
- [ ] Unapproved vendor gets 403
- [ ] Overlap with more than 24 hours left returns 409
- [ ] Expired boosts leave paid placement right away

---

### Step 9: Payments (Paystack)

**Endpoints**: `/payments/initialize`, `/payments/webhook`

**Rules**
- Initialize creates a pending payment and returns the Paystack reference and access code
- Webhook verifies the signature, checks the amount matches the payment record, marks it success and activates the boost, all in one transaction
- Payment statuses: pending, success, failed, refunded

**Done when**
- [ ] Invalid signature returns 401 and nothing changes
- [ ] Wrong amount is rejected and the boost stays pending
- [ ] The same webhook twice activates the boost once
- [ ] Frontend success without a webhook leaves the boost pending

---

### Step 10: Vendor dashboard

**Rules**
- Record `impression`, `view` and `contact_tap` events, linked to the boost in effect
- The vendor's own views do not count. Repeat views by the same viewer within 30 minutes count once
- Return views, search appearances and contact taps this week, rating, review count, active boost with countdown, boost history with results per boost

**Done when**
- [ ] One view recorded per customer per 30 minutes
- [ ] Active boost shows zones, end time and results so far

---

### Step 11: Notifications

**Rules**
- Resend, sent from a background job with up to 3 retries using the `email_jobs` table
- Emails: verification code, welcome, password reset, profile pending, approved, rejected (with reason), suspended, boost live, boost expiring, hire follow up
- An email failure never blocks the main action

**Done when**
- [ ] Each trigger sends its email exactly once
- [ ] A failed send is logged and retried, and the main action still succeeds

---

### Step 12: Admin

**Endpoints**: `/admin/vendors/pending`, `/admin/vendors/:id/approve`, `/admin/reviews/reports`, plus the rest of the admin area

**Rules**
- Vendor queue with NIN result, last 4 digits and photos. Approve, reject with a reason, suspend, reinstate
- Suspend or reinstate accounts
- Manage categories, zones, multipliers and boost prices. Deactivating a zone stops new boosts only
- Revenue summary and all payments, including failed and refunded
- Review moderation, user lookup, location cooldown override
- Every admin action writes to `audit_logs`

**Done when**
- [ ] Non admin on any `/admin` route gets 403
- [ ] Every admin action creates an audit log row
- [ ] Suspended profile disappears from search and `/p/:slug`

## 9. Error handling

Every error uses one shape:

```json
{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "...", "fieldErrors": {} } }
```

| Status | When |
|---|---|
| 400 | Validation errors, with field level detail |
| 401 | Not logged in or session expired |
| 403 | Wrong role, unverified email, or unapproved profile, with a message saying what to do |
| 404 | Not found, including unapproved or suspended profiles viewed by anyone but the owner |
| 409 | Duplicates: email, second review, second reply, overlapping boost, reused Paystack reference |
| 429 | Rate limits: login, OTP, NIN, daily contact reveals |
| 500 | Server error, logged with a request ID. Never return a stack trace |

## 10. Never do this

- Never store or log a full NIN
- Never return phone or WhatsApp outside the contact endpoint
- Never return a password or password hash
- Never activate a boost from anything except a verified webhook
- Never store money as a float
- Never commit `.env` or secrets
- Never hard delete categories or zones
- Never let the frontend compute prices or ranking
